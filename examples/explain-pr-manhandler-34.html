A change map for the PR that closed the ways the crew could fake a landed change or merge over unverified CI.

The big idea

This PR closes three ways manhandler's state could lie: a worker could forge a "landed" signal, the merge command could merge before CI reported, and a crash could wedge the lock every future write depends on. It hardens the shared toolbelt so a state that looks done is actually done.

1Why: state that could lie

manhandler runs a crew of agents against your repos and tracks each task's state — working, landed, done — from real signals it records. That tracking is trusted: a task reported done can have its local copy cleaned up. So any way to forge a terminal signal is a correctness and safety hole. This PR (closing issues #20 and #21) found and closed several:

  • A worker could append a fake merged event, or hand-write the pr_state field, and be reported done over unlanded work.
  • The merge command treated no checks reported as a pass — so it could merge in the window after a PR opens but before CI registers, i.e. merge red without knowing it.
  • A worker crash (SIGKILL) left the shared lock dir behind, wedging every future write for ~30s and then failing hard.
  • An out-of-band merge (you merging in the GitHub web UI) was never seen, so the task read working forever.
📌 Context

Everything here lives in bin/mh-*.sh, the toolbelt scripts. bin/mh-lib.sh is the shared library the others source — so a fix in mh-lib is a fix for the whole fleet.

2The change map

Five files changed, clustered by concern. The shared library (bin/mh-lib.sh) gained the crash-safe lock plus two small pure helpers; the command scripts (mh-task, mh-pr, mh-worktree) call into them and add their own guards; and tests/smoke.sh pins the new behavior.

Line counts per file: mh-lib.sh +97/−9, mh-pr.sh +28/−10, mh-task.sh +26/−1, mh-worktree.sh +7/−0, tests/smoke.sh +72/−1.

Cluster A — the forged landing signal (#20)

Two entry points that a worker controls now refuse to write a landing signal. In mh-task.sh, event merged is rejected (only the sanctioned landing paths append it, directly via the status helper), and set refuses the PR-tracking fields pr, pr_state, merge_state. In mh-worktree.sh, create now fails closed if there is no task record with a kind — otherwise it would write a meta the state logic cannot classify.

Cluster B — never merge red (#21)

The merge decision moved into a pure helper, mh_merge_gate, in mh-lib.sh, and mh-pr.sh merge now calls it. See step 3.

Cluster C — seeing an out-of-band merge

mh_refresh_pr_state (new, in mh-lib.sh) refreshes the cached pr_state from GitHub before a state decision, so a web-UI merge is seen. Both mh-task.sh state and mh-worktree.sh landed call it; the bulk mh-task.sh list deliberately stays offline to avoid N network round-trips on the hottest command.

Cluster D — the crash-safe mutex (#21)

mh_lock / mh_unlock in mh-lib.sh learned to reclaim a lock abandoned by a crashed holder, and to clean up on INT/TERM. See step 4.

3The merge gate: never merge red

Before this PR, a none rollup — no checks reported — was lumped in with passing and allowed to merge. But none is ambiguous: it might mean "this repo has no CI", or it might mean "CI hasn't registered yet". You can't tell them apart from a missing .github/workflows, because CI can be an external provider posting commit statuses. So none no longer auto-passes.

Extracting the decision as a pure function is the load-bearing move: it can be tested offline against every rollup value without touching GitHub. The prose form of the branches:

mh_merge_gate passing  0  -> allow
mh_merge_gate failing  0  -> refuse-failing
mh_merge_gate pending  0  -> refuse-pending
mh_merge_gate none     0  -> refuse-none        # was: auto-pass (the bug)
mh_merge_gate none     1  -> allow              # --allow-no-checks
mh_merge_gate bogus    0  -> refuse-unknown
✅ Also here

mh-pr.sh push now turns a rejected push (a branch that was rebased and diverged from origin) into a plain domain error instead of raw git text — and it never force-pushes. A divergence is a signal to reconcile, not to overwrite.

4The mutex: surviving a crash

manhandler serializes shared-state writes (the registry, task meta, memory) with a mkdir-based lock — flock is absent on macOS. The problem: a holder killed with SIGKILL can't run its cleanup, so the lock dir survives and wedges everyone. The fix records the holder's PID inside the lock dir, and lets a waiter reclaim it only on positive evidence of abandonment.

Two subtle points make this safe. First, reclaimers serialize through a second lock and re-verify the same dead PID still owns the dir immediately before removing it, so two waiters can't both reclaim and a live takeover isn't torn away. Second, the INT/TERM handlers now clean up and exit — without the explicit exit, bash would run the handler and then resume the now-unlocked critical section, letting a waiter write concurrently.

⚠️ The one case left visible

A holder that crashes in the microsecond between its mkdir and writing its PID leaves an empty PID — not evidence — so it is not reclaimed and falls through to the visible ~30s timeout. That is deliberate: guess wrong and you tear a live lock. Fail loud beats fail silent.

5Approach & notable decisions

The through-line is make the trusted signal unforgeable and the risky decision pure:

  • Single owner per fact. Landing fields are written only by mh-pr/mh-merge; the generic mh-task set and event now reject them. One writer, no drift.
  • Pure decisions, offline tests. mh_merge_gate is a pure string-in / string-out function, so the never-merge-red rule is exercised for every rollup value without a network call.
  • Fail closed, fail loud. A kind-less worktree create is refused; an ambiguous none rollup is refused; an unreclaimable lock times out visibly. No silent fallback that fakes success.
  • Offline by default on hot paths. The live PR refresh runs on a single state/landed call, but list and the session digest stay offline (MH_NO_FETCH=1).
  • Union-merge-friendly tests. The new smoke checks sit in one clearly-marked block at the end of tests/smoke.sh so parallel branches merge cleanly.

6What to review / risk

The load-bearing, highest-risk changes to read closely:

  • bin/mh-lib.sh — the mutex reclaim loop. This is concurrency and cleanup logic; the reclaim re-verify and the exiting signal handlers are the parts that must be exactly right. The smoke block covers a dead-PID reclaim and that a live lock stays exclusive, but full concurrent races are hard to pin in a smoke test.
  • bin/mh-pr.sh merge — the gate call. Verify the behavior change is intended: repos with genuinely no CI now need --allow-no-checks to merge. The pure mh_merge_gate is fully covered; the surrounding mh-pr plumbing and gh-axi calls are not (no automated coverage for the live PR path).
  • The live-refresh cost. mh_refresh_pr_state adds a GitHub round-trip to a single state/landed call. Confirm the offline guards on list hold, or the session digest slows to N network calls.
📌 Test coverage, honestly

The added tests are all offline: GitHub-dependent paths are exercised via their pure decision helpers, not the network. The forged-signal, kind-less-create, merge-gate, forged-pr_state, and mutex-reclaim behaviors each have checks; the live GitHub calls in mh-pr remain manually verified only.

Glossary

Landing signal
The trusted marker that a task's work has actually landed (a merged PR or a completed local land). If forgeable, a task can be reported done over unlanded work.
Merge gate
The decision that permits or refuses a merge based on CI. Now the pure function mh_merge_gate — never merge red.
Rollup
The single summarized CI status for a PR: passing, failing, pending, or none (no checks reported).
pr_state
The cached PR status field on a task's meta. Goes stale on an out-of-band merge, so it is refreshed live before a state decision.
Out-of-band merge
A merge done outside manhandler — e.g. in the GitHub web UI — which the cached state would otherwise never see.
Mutex
The advisory lock (a mkdir-created dir) that serializes shared-state writes, since flock is unavailable on macOS.
Reclaim
A waiter safely removing a lock left behind by a crashed holder, on proof the holder's PID is dead.
Fail closed
When inputs are ambiguous or missing, refuse rather than guess — e.g. a kind-less worktree create, or a none rollup.

Check your understanding

Why can't a worker just write pr_state MERGED to look done?

Because mh-task.sh set now refuses the PR-tracking fields, and event merged is rejected too. Only mh-pr/mh-merge — which derive the value from GitHub — may write the landing signal.

Why doesn't a none rollup count as "safe to merge"?

none can't be told apart from "CI hasn't reported yet", and CI may be an external provider with no .github/workflows to detect. Auto-passing it could merge red, so it passes only with an explicit --allow-no-checks.

Why must the INT/TERM handlers exit, not just clean up?

Otherwise bash runs the handler and resumes the now-unlocked critical section — letting a waiter acquire the lock and write at the same time. Exiting after cleanup closes that concurrency window.
