How the TCP three-way handshake works

The three-message conversation that has to happen before two computers can trade a single byte of real data — and why it takes exactly three.

Difficulty: Beginner–Intermediate Prerequisites: what a client and a server are ~7 min read

The big idea

Before two computers can reliably exchange data, they have to agree on two things at once: that they're both here and ready, and which numbers they'll use to order every byte and notice anything lost. The three-way handshake is that mutual agreement — settled in exactly three messages: SYN → SYN-ACK → ACK.

1Why you can't just start sending

The internet underneath TCP is best-effort: it will try to deliver your packets, but it makes no promises. A packet can be dropped, duplicated, delayed, or arrive out of order — packet 3 might show up before packet 1. Nothing at that lower layer fixes this for you.

So imagine the client just starts blasting data at the server. Two things go wrong. First, the server might not even be listening yet — the data lands on a closed door and is thrown away. Second, even if it is listening, when pieces arrive scrambled the server has no way to know the intended order, or that a piece is missing at all.

TCP's answer is to talk before sending real data. The two sides use a few small control messages to confirm "yes, I'm here and ready," and to each pick a starting number so that from then on every byte has a well-defined position in line. That short opening conversation is the handshake.

📌 Why not just two messages?

A TCP connection is full-duplex — data flows both ways independently, so each direction needs its own agreed starting number. The client must confirm the server's number, and the server must confirm the client's. Two messages can only get one of those confirmations home; three is the minimum that gets both.

2Message 1 — SYN: the client proposes a starting number

The client sends a small segment (a TCP message) with the SYN flag turned on. SYN is short for synchronize, and the thing being synchronized is the sequence number. The client picks an initial sequence number — call it x — and says, in effect, "I want to open a connection, and I'll start numbering my bytes from x."

It sends this to a specific port on the server (port 443 for HTTPS, say) so the right program receives it. After sending, the client is waiting for a reply — this state is called SYN-SENT.

📌 Why not just start at 0?

The starting number is chosen semi-randomly, not fixed at 0. That makes it much harder for an outsider to guess valid sequence numbers and inject fake data, and it avoids confusion with stray packets from an earlier connection on the same ports.

3Message 2 — SYN-ACK: the server agrees and proposes its own

If the server is listening on that port and willing to accept the connection, it replies with a single segment that does two jobs at once — it has both the SYN and the ACK flags set:

  • The ACK (acknowledge) part says "I got your SYN." It carries an acknowledgement number of x + 1 — meaning "the next byte I expect from you is number x + 1." (Why +1? The SYN itself counts as one number in the sequence, so x is used up and x + 1 is what comes next.)
  • The SYN part is the server doing its own proposing: it picks its own initial sequence number y for the data it will send back to the client.

One message, both halves of the deal: the server confirms the client's number and offers its own. The server is now in a state called SYN-RECEIVED.

4Message 3 — ACK: the client agrees back, and it's ESTABLISHED

The client now does the mirror image of what the server just did: it acknowledges the server's number. It sends a segment with the ACK flag set and an acknowledgement number of y + 1 — "I got your SYN too; the next byte I expect from you is y + 1."

That's the third message. Now both sides have had their starting number confirmed by the other, so both know exactly how to number and check everything that follows. The connection is ESTABLISHED, and data can flow in both directions.

It helps to watch the client walk through its states: it starts CLOSED, moves to SYN-SENT the moment it sends message 1, and reaches ESTABLISHED once it has received the SYN-ACK and sent its ACK. (The server travels a parallel path: LISTEN → SYN-RECEIVED → ESTABLISHED.)

💡 Analogy: a radio check

It's the "can you hear me?" you do before talking on a two-way radio:

SYN — Client: "Can you hear me?"
SYN-ACK — Server: "Yes, I hear you. Can you hear me?"
ACK — Client: "Yes, I hear you too."

After that exchange each side knows the other can both hear and be heard — so it's safe to start the actual conversation. Two lines wouldn't be enough: the client would never have learned that the server can hear it.

5What the sequence numbers actually buy you

The handshake isn't just a polite greeting — those two agreed starting numbers are the machinery that makes TCP reliable. Once both sides number their bytes from a known point, the numbers give you three things for free:

  • Ordering. Every byte has a sequence number, so the receiver can reassemble the stream in the right order even if packets arrive scrambled.
  • Loss and duplicate detection. A gap in the numbers means something is missing (and gets re-sent); a number already seen means a duplicate (and gets discarded).
  • Full-duplex flow. Because each direction has its own agreed number line (x… one way, y… the other), both sides can send at the same time without their streams getting confused.

A worked example, with real numbers

Say the client picks x = 1000 and the server picks y = 5000. Here is the whole handshake, spelled out:

1. Client → Server   SYN       seq=1000
     "Let's talk. My bytes start at 1000."

2. Server → Client   SYN-ACK   seq=5000  ack=1001
     "Got it (next from you = 1001). My bytes start at 5000."

3. Client → Server   ACK       seq=1001  ack=5001
     "Got it (next from you = 5001)."

   → ESTABLISHED. If the client now sends 100 bytes of data,
     they are numbered 1001–1100, and the server will reply
     with ack=1101 ("give me byte 1101 next").

Notice the +1 pattern: the server acknowledges 1001 (not 1000) because the client's SYN consumed number 1000, and the client acknowledges 5001 because the server's SYN consumed 5000. Each SYN counts as one "byte" for numbering purposes.

✅ The one-sentence version

Three messages, because a reliable two-way connection needs both sides to confirm both starting numbers — and three is the fewest that gets that done.

Glossary

Segment
One TCP message — the unit TCP sends, carrying flags (like SYN/ACK), sequence numbers, and possibly data.
SYN
A flag meaning "synchronize." Set on the messages that propose a starting sequence number and open the connection.
ACK
A flag meaning "acknowledge." Its acknowledgement number says which byte the sender expects next, confirming everything before it arrived.
Sequence number
The position of a byte in one direction's stream. Both sides pick a starting value during the handshake.
Port
A number identifying which program on a machine a connection is for (e.g. 443 for HTTPS), so messages reach the right listener.
Full-duplex
Both directions carry data independently and at the same time — two number lines, one per direction.
ESTABLISHED
The state after all three messages: both starting numbers are confirmed and real data can flow.

Check your understanding

Why three messages and not two?

Because the connection is full-duplex, so both starting numbers must be confirmed. The client's SYN and the server's SYN-ACK confirm the client's number and propose the server's — but the server still needs proof its own number arrived. The client's final ACK is that proof. Two messages leave one side's number unconfirmed.

Why does the server acknowledge x + 1 and not x?

The acknowledgement number names the next byte expected, not the last one received. The SYN itself counts as one number in the sequence, so it uses up x; the next thing the server expects is therefore x + 1.

The handshake finishes, but the first data packet arrives before an earlier one. Is the connection broken?

No — this is exactly what the sequence numbers are for. Each byte carries its position, so the receiver buffers the out-of-order piece and reassembles the stream correctly once the gap fills in. A truly missing piece shows up as a gap in the numbers and gets re-sent.

Where to go next

  • Closing a connection — the teardown is its own small handshake using the FIN flag (FIN → ACK each way). Because each direction closes independently, it's often four messages, not three.
  • What TLS adds on top — the TCP handshake only sets up a reliable pipe; it does nothing for privacy. TLS runs after it to negotiate encryption keys, so an HTTPS request pays for both handshakes before any page data moves.
  • Congestion control — once ESTABLISHED, TCP doesn't just fire data as fast as it can; algorithms like slow start and CUBIC ramp the rate up and back off on loss to avoid overwhelming the network.
  • For the exact rules, read the source of truth: RFC 9293, the current TCP specification.
